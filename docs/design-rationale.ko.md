# Motive 설계 근거 (Design Rationale)

> **이 문서는 Motive를 왜 이렇게 만들었는지 설명합니다.**
> `stable-semantics.md`가 *무엇이 안정적인 의미인가*를 기록한다면, 이 문서는 그 의미를 선택한 *이유*와 *맥락*을 기록합니다.
> 분류: **[RATIONALE]** — 설계 결정의 근거. 소스 코드나 테스트가 아닌 프로젝트 판단을 반영합니다.
>
> English version: [docs/design-rationale.md](design-rationale.md)

---

## 1. Motive는 무엇인가

Motive는 **모델 중심(model-centric) 소프트웨어 실행 런타임**입니다.

- **모델이 추론과 계획을 수행**합니다.
- **Motive는 워크스페이스, 도구, 실행, 개정(revision) 추적을 제공**합니다.

이것이 전부입니다. 에이전트 프레임워크, 플러그인 시스템, 플래너 레이어, 서브에이전트, 메모리 매니저는 의도적으로 포함하지 않습니다.

---

## 2. 실행 루프 — 어떻게 작동하는가

```
사용자 요청
  → 컨텍스트 컴파일
  → OpenAI 호환 모델
  → 모델 응답과 도구 호출
  → 도구 실행
  → 런타임 관측
  → 반복
  → 최종 응답
```

각 반복은 **스텝(step)**입니다. 스텝, 시간, 도구 호출 수는 **실행 예산(execution budget)**으로 제한되며, 예산 초과 시 실행이 중단됩니다.

---

## 3. 왜 Stateless 인가

> 각 사용자 요청은 **신선한 모델 컨텍스트(fresh model context)**로 시작됩니다.
> Motive는 실행을 위해 보이지 않는 채팅 기록에 의존하지 않습니다.

영속적 세계는 채팅 기록이 아니라 **워크스페이스와 Git**입니다. 모델 컨텍스트는 일회용 작업 공간입니다.

### 세션 복구

세션 트랜스크립트는 **컨텍스트가 아니라 기록**입니다. 중단된 실행 뒤에는 이후 실행이 현재 사용할 수 있는 evidence를 확인하고 무엇을 할지 스스로 판단할 수 있습니다. Motive는 계속, 재시도, 재계획 또는 다른 복구 전략을 강제하지 않습니다.

---

## 4. 맥락(Context)은 어떻게 파악하는가

`Runtime.ContextBlock()`은 워크스페이스 위치, Git 상태, 제한된 파일 목록과 적용되는 시스템 가이드를 제공합니다. 모델은 필요할 때 도구를 사용해 파일을 직접 검사합니다.

초기 컨텍스트에는 전체 워크스페이스나 이전 대화 기록을 의도적으로 포함하지 않습니다.

---

## 5. 왜 이렇게 작성했는가

Motive는 에이전트 프레임워크, 플러그인 시스템, 플래너 레이어, 서브에이전트, 메모리 매니저를 의도적으로 포함하지 않습니다.

모델이 추론하고 작업 수행 방식을 선택합니다. Motive는 실행 환경을 제공하며 모델이 다음에 무엇을 해야 하는지 판단하지 않습니다.

워크스페이스와 Git은 실행의 가시적인 기준점과 변경 사항의 견고한 기록을 제공합니다. 이후 실행은 숨겨진 모델 컨텍스트를 복원하지 않고 이 evidence를 직접 검사할 수 있습니다.

---

## 6. 왜 Compaction을 하지 않는가

Compaction은 하나의 실행이 다룰 수 있는 컨텍스트의 천장을 높일 뿐, 숨겨진 컨텍스트를 견고한 영속 상태로 만들지는 않습니다.

따라서 Motive는 이전 모델 컨텍스트를 압축하거나 복원하지 않습니다. 각 실행은 신선하게 시작합니다. 실행이 종료되거나 중단된 뒤 추가 작업이 가능하다면 이후 실행은 워크스페이스, Git 상태 및 사용할 수 있는 session evidence를 검사하고 무엇을 할지 스스로 판단할 수 있습니다.

Motive는 **작업을 분할해야 하는지, 어떻게 분할해야 하는지, 다음 실행이 계속할지·파기할지·재시도할지·재계획할지·사용자에게 질문할지를 결정하지 않습니다.**

> **요약은 요약자의 편향을 담습니다. 신선한 재판단은 사용할 수 있는 evidence를 직접 읽습니다.**

---

## 7. Motive의 고유한 시스템

### 세션 = 트랜스크립트, 컨텍스트가 아님

세션은 관측 가능한 실행 이벤트를 기록하는 JSONL입니다. 숨겨진 모델 컨텍스트로 복원되지 않습니다. 필요할 경우 모델은 `session_log`를 통해 사용할 수 있는 세션 evidence를 검사할 수 있습니다.

### 런타임 관측

실행 중 Motive는 스텝 사용량, 도구 사용량, 실패, 경과 시간, revision 변화와 같은 기계적 사실을 제공합니다. 이 관측은 작업 전략을 결정하지 않고 실행 상태를 드러냅니다.

### Git Revision 기록

실행은 관측 가능한 revision boundary를 기록하므로 이후 작업이 무엇이 변경됐는지 검사할 수 있습니다.

### 사용자 개입

사용자는 활성 실행을 조정하거나 이후 입력을 대기시킬 수 있습니다. 그 입력이 작업에 어떤 영향을 미칠지는 모델이 판단합니다.

### Bounded Execution

스텝, 시간, 도구 호출은 안전 제한으로 bounded됩니다. 이것은 **semantic task boundary나 모델의 추론 정책이 아니라 실행 경계**입니다.

---

## 8. 강점 요약

| 항목 | Motive |
|---|---|
| 상태 관리 | 워크스페이스 + Git을 견고한 evidence로 사용, execution마다 신선한 모델 컨텍스트 |
| 세션 영속성 | 트랜스크립트 기록, 컨텍스트 복원 없음 |
| 계획 | 전적으로 모델 주도 |
| 컨텍스트 관리 | Compaction 및 숨겨진 history 복원 없음 |
| 실행 예산 | 스텝, 시간, 도구 호출 bounded |
| 실행 격리 | 관측 가능한 workspace와 Git revision boundary |
| 복구 | 이후 execution이 evidence를 보고 다음 행동을 스스로 판단 |
| 확장 | 독립적인 bounded execution; 런타임이 decomposition 전략을 규정하지 않음 |

중심 원칙은 다음과 같습니다.

> **Motive는 실행 경계와 관측 가능한 evidence를 보존한다. 사용자의 작업을 재해석하거나 모델이 작업을 수행하는 전략을 규정하지 않는다.**
